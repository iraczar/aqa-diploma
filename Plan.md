# План автоматизации тестирования сервиса покупки тура

## 1. Автоматизируемые сценарии
Обе формы («Купить» и «Купить в кредит»), по 6 сценариев на форму:
1. Успешная операция с картой APPROVED, проверка записи APPROVED в БД.
2. Отказ по карте DECLINED, проверка записи DECLINED в БД.
3. Отправка пустой формы.
4. Номер карты неполной длины.
5. Истёкший срок действия (год в прошлом).
6. Недопустимый месяц (13).

## 2. Инструменты и обоснование
- Java 17, Gradle: стандарт курса, простая сборка.
- JUnit 5: параметризация, аннотации, интеграция с Allure.
- Selenide: устойчивые ожидания, лаконичные UI-тесты.
- commons-dbutils + JDBC: простые запросы к БД, драйверы MySQL и PostgreSQL.
- Docker Compose: быстрый запуск MySQL и PostgreSQL.
- Allure и Gradle-отчёты: наглядные отчёты со скриншотами.
- Git/GitHub: хранение кода, документов и issues.

## 3. Риски
- Нестабильность общего банковского симулятора (доступность, задержки до 10 с).
- Изменение вёрстки: селекторы привязаны к классам библиотеки интерфейса.
- Баги самого приложения могут блокировать позитивные сценарии.
- Различия MySQL и PostgreSQL в настройке окружения.
- Окружение (Docker, браузер) на машине проверяющего.

## 4. Оценка времени (интервал с учётом рисков)
- Настройка окружения и проекта: 3–5 ч.
- Ручное тестирование и баг-репорты: 4–6 ч.
- Написание автотестов и работа с БД: 8–12 ч.
- Отчёты (Allure, Gradle), README: 2–4 ч.
- Итоговые документы: 2–3 ч.
- Итого: 19–30 ч.

## 5. План сдачи
- День 1–3: план (этот файл), окружение.
- День 4–6: ручное тестирование, issues, Report.md.
- День 7–10: автотесты, прогон, Allure.
- День 11–12: Summary.md, README, финальная проверка.
